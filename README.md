# Telegram Collector

Инструмент для сбора и хранения переписки из Telegram-чатов с возможностью выгрузки данных через Telegram-бота.

## Что делает

- Подключается к Telegram через TDLib (tdlib/tdjson) под реальным аккаунтом
- Скачивает историю всех чатов и слушает новые сообщения в реальном времени
- Сохраняет сообщения, вложения и реакции в PostgreSQL с полной историей правок и удалений
- Параллельно запускает Telegram-бот для администраторов, через который можно выгрузить переписку в Excel
- Фоновым worker'ом анализирует тексты сообщений через YandexGPT (корректность, вежливость, токсичность, риски утечки данных и т. д.) и считает метрики скорости ответов

```

│   ├── auth.py               — машина состояний авторизации TDLib

│   └── connection.py         — мониторинг состояния соединения и прокси
│
├── telegram_admin/           — Telegram-бот для администраторов
│   ├── bot.py                — сборка Application, фоновый поток polling'а
│   ├── commands.py           — хендлеры команд (/start, /chats, /export)
│   └── keyboards.py          — inline-клавиатуры
│
├── database/
│   ├── models.py             — SQLAlchemy ORM (User, Chat, Message, ...)
│   ├── repository.py         — вся работа с БД (DatabaseRepository)
│   └── init_db.py            — create_engine / sessionmaker / create_all
│
├── yandex/
│   └── worker.py             — QualityWorker: очередь анализа, клиент YandexGPT, метрики
└── core/
    ├── config.py             — загрузка переменных окружения в датаклассы
    └── logger.py             — настройка logging (файл + консоль)
```
Всё работает в одном процессе, но в разных потоках:
 
| Поток | Что делает |
|---|---|
| главный | TDLib-цикл в `main.py` (получение и обработка update'ов) |
| `admin-bot` | Telegram-бот со своим event loop'ом |
| `quality-worker` | Анализ сообщений через LLM и расчёт метрик (запускается, только если заданы ключи Yandex) |
 
Каждый поток работает со своей собственной Session SQLAlchemy (сессии не шарятся между потоками).

## База данных

### Сбор переписки

| Таблица | Назначение |
|---|---|
| `users` | Авторы сообщений |
| `chats` | Чаты |
| `messages` | Актуальное состояние каждого сообщения |
| `message_revisions` | Лог изменений: `created` / `edited` / `deleted` |
| `attachments` | Вложения (фото, документы, видео, голосовые) |
| `reactions` | Реакции с полным списком авторов |

Удалённые сообщения помечаются флагом `is_deleted`, но не удаляются из базы. История правок хранится в `message_revisions` — одна строка на событие, ничего не перезаписывается.

Реакции хранятся как журнал событий: при появлении реакции добавляется строка `added`, при снятии — строка `removed`. Для чатов, где Telegram не отдаёт полный список авторов, используется запасной путь через `recent_sender_ids`.

### Анализ качества
 
| Таблица | Назначение |
|---|---|
| `analysis_jobs` | Очередь анализа: одна задача на ревизию сообщения и версию пайплайна. Статусы: `pending`, `processing`, `completed`, `failed`, `superseded` |
| `quality_findings` | Замечания, найденные моделью: категория, серьёзность, уверенность, цитата, объяснение, рекомендация, статус проверки (`pending_review` / `confirmed` / `rejected`) |
| `quality_metrics` | Метрики скорости ответов между сообщениями (`explicit_reply` / `next_message_estimate`) |

## Анализ качества сообщений
 
За анализ отвечает `QualityWorker` (`yandex/worker.py`). Цикл работы:
 
1. Восстанавливает «зависшие» задачи (`processing` дольше 15 минут).
2. Ставит в очередь новые ревизии сообщений (`created` / `edited`) с непустым текстом.
3. Забирает пачку задач (`SELECT ... FOR UPDATE SKIP LOCKED`) и отправляет текст в YandexGPT вместе с небольшим контекстом: текст сообщения, на которое был reply, и 3 предыдущих сообщения чата (авторы обезличены — только «тот же автор» / «другой»).
4. Проверяет ответ модели: допустимые категории и уровни серьёзности, `confidence` в диапазоне 0–1, а цитата (`evidence`) должна дословно присутствовать в сообщении. Не более 5 замечаний на сообщение.
5. Сохраняет замечания в `quality_findings` и закрывает задачу.
6. Раз в 10 минут пересчитывает метрики скорости ответов.
**Категории замечаний:** `correctness`, `politeness`, `toxicity`, `communication_style`, `corporate_policy`, `clarity`, `privacy_risk`. Дополнительно используется служебная категория `model_refusal` — если модель отказалась анализировать сообщение (сработал content filter), оно не теряется, а отправляется на ручную проверку.
 
**Что не отправляется в LLM:** голосовые сообщения без подписи (плейсхолдер), слишком короткие тексты и сообщения без букв.
 
**Ошибки и повторы:** при сбое задача повторяется с экспоненциальной задержкой (базово 60 секунд, максимум 1 час), до 5 попыток, после чего получает статус `failed`.
 
**Метрики скорости ответов:**
- `explicit_reply` — точное время ответа на reply другого автора;
- `next_message_estimate` — оценка для сообщений без reply: время до предыдущего сообщения другого автора (не старше 6 часов). Не учитывает нерабочее время и не гарантирует, что человек отвечал именно на то сообщение.
> ⚠️ **Конфиденциальность:** тексты сообщений (и контекст) передаются во внешний сервис YandexGPT. Убедитесь, что это допустимо для анализируемых чатов. Результаты модели — это кандидаты на проверку человеком, а не выводы о сотрудниках.
 
Если `YANDEX_API_KEY` и `YANDEX_FOLDER_ID` не заданы, worker не запускается (в лог пишется предупреждение), а сбор Telegram работает как обычно.

## Требования

- Python 3.11+
- PostgreSQL
- Библиотека tdjson (TDLib 1.8.x, собранная под вашу платформу)
- Telegram API credentials (api_id / api_hash) — получить на [my.telegram.org](https://my.telegram.org)
- Telegram Bot Token — создать через [@BotFather](https://t.me/BotFather)
- API-ключ и идентификатор каталога Yandex Cloud для анализа качества

## Запуск

```bash
python main.py
```

При первом запуске TDLib потребует ввести код подтверждения из Telegram (в консоль). После авторизации сессия сохраняется в `tdlib/<md5_от_номера>/` и повторного ввода кода не потребуется.

База данных создаётся автоматически при каждом старте (`create_all` — безопасно, не трогает существующие таблицы).

Остановка — `Ctrl-C`: worker и бот завершаются корректно.

## Telegram-бот (для администраторов)

Доступ имеют только пользователи из `ADMIN_IDS`.

| Команда | Описание |
|---|---|
| `/start` | Информация о боте и статус доступа |
| `/chats` | Список чатов в базе |
| `/export` | Выбрать чат и период, получить Excel-файл |
| `/quality` | Выбрать чат и период, получить Excel-отчёт о проблемах качества |
| `/cancel` | Отменить текущую операцию |

Период выбирается кнопками (сегодня / 7 дней / 30 дней) либо вводится вручную в формате `2026-06-01 2026-06-25`. Все даты — в UTC.

Выгрузка (`/export`) формирует `.xlsx` с тремя листами: **Сообщения**, **Вложения**, **Реакции**. В выгрузку попадают в том числе удалённые сообщения (с пометкой в колонке «Удалено»).

**Отчёт `/quality`** формирует `.xlsx` с двумя листами:
- **Замечания** — найденные проблемы: сообщение, отправитель, категория, серьёзность, уверенность, цитата, объяснение, рекомендация, статус проверки;
- **Скорость ответов** — по каждому сотруднику и типу метрики: количество, медиана, среднее и P90 (в минутах).
В подписи к файлу показывается статус очереди анализа (сколько задач `pending`, `completed` и т. д.) — это помогает понять, обработан ли выбранный период полностью.

## Логирование

Все события пишутся одновременно в консоль и в `logs/collector.log` (ротация по 10 МБ, 5 файлов). Нативные логи TDLib — в `logs/tdlib_native.log` (также 10 МБ). Необработанные исключения верхнего уровня и ошибки внутри основного цикла тоже попадают в лог, а цикл продолжает работу.

Ключевые префиксы в логах:

| Префикс | Что означает |
|---|---|
| `AUTH:` | Шаги авторизации TDLib |
| `CONNECTION:` | Смена состояния соединения |
| `PROXY:` | Проблемы с прокси |
| `ADMIN BOT:` | События Telegram-бота |

## Важные особенности

**Сессии TDLib** хранятся отдельно для каждого номера телефона (путь включает MD5 от номера) — смена `PHONE_NUMBER` в `.env` не подхватит чужую сессию автоматически.

**Время** во всей базе хранится как naive UTC (`tg_date`, `deleted_at`, `received_at` и т. д.), фильтры периодов в боте тоже работают в UTC.

**Реакции** запрашиваются постранично через `getMessageAddedReactions`. Для одного сообщения в любой момент времени идёт не более одного цикла запросов, чтобы исключить гонку при параллельных обновлениях.

**Сессии SQLAlchemy** не расшариваются между потоками: каждый вызов к БД из бота открывает и закрывает собственную короткоживущую Session.

**Очередь анализа** привязана к ревизии сообщения: правка текста создаёт новую задачу, а повторная обработка уже проанализированной ревизии не происходит (уникальность по сообщению, ревизии и версии пайплайна).

**Схема БД** создаётся автоматически при старте. При изменении существующих таблиц `create_all` не применяет ALTER — для этого нужен Alembic.
